A 1D CNN for Pulse-Count Estimation in Simulated GRB Light Curves

Abstract

We describe a pipeline that (1) generates synthetic Swift/BAT-like gamma-ray burst (GRB) light curves using the existing Stern & Svensson (1996, SS96) pulse-avalanche simulator in this repository, (2) labels each simulated light curve with the number of independent parent pulses that seeded its avalanche, and (3) trains a one-dimensional convolutional neural network (1D CNN) to predict that count directly from the observed (noisy, background-subtracted) count-rate time series. We report the implementation issues that had to be resolved in the existing codebase before this was possible, the design decisions behind the labeling scheme, network architecture, and training procedure, and the evaluation methodology used to validate the trained model. Full reproduction instructions and a file-by-file description of the code are included below.

1. Background and Objective

The pulse-avalanche model reproduces the ensemble statistical properties of GRB light curves by simulating a stochastic cascade: a Poisson-distributed number of independent "parent" pulses trigger, and each recursively spawns a cascade of temporally-clustered "child" pulses (Stern & Svensson 1996; implemented in lc_pulse_avalanche/avalanche.py). The existing repository already provides a genetic-algorithm-calibrated parameter set that reproduces real Swift/BAT and BATSE light-curve statistics, and a script (simulate_GRBs.py) that draws synthetic light curves from that model.

Our objective is a supervised learning problem layered on top of that simulator: given only the observed time series of a synthetic light curve, predict how many distinguishable pulses ("peaks") it contains. Because the simulator has privileged access to the number of parent pulses that seeded each realization, it can generate an effectively unlimited, exactly-labeled training set — the central appeal of using a physically-motivated simulator as a source of ground truth for this kind of counting task.

2. Methods

2.1 Ground-truth label: number of parent pulses

The natural candidate label already present in this codebase, n_sig_pulses — the number of pulses judged "significant" by a MEPSA-like detectability criterion (count_significative_pulses_ver2 in statistical_test.py) — could not be used: that function reads an LC attribute (lc._ampl) that no longer exists in the current pulse-generation code (see §3.2). We therefore used the number of parent (spontaneous) pulses, mu_s in avalanche.py's notation, as the training label. This quantity was already computed by the simulator on every run but was previously a local variable, discarded once the avalanche was generated.

This choice is physically motivated, not merely a workaround: each parent pulse's cascade of children is temporally clustered around its own trigger time, so in the observed (post-overlap, post-noise) light curve, one parent typically manifests as one distinguishable bump. The number of parent pulses is therefore a reasonable proxy for "the number of peaks a human, or a CNN, would count by eye" — arguably a cleaner target than a detectability threshold tuned to a specific instrument's sensitivity.

2.2 Data generation

Light curves were generated with the existing simulate_GRBs.py config.ini pipeline, unmodified apart from the labeling additions described in §3.1. The instrument was fixed to Swift/BAT, using the paper's existing GA-calibrated parameters (v36): mu=1.34, mu0=1.16, alpha=2.53, delta1=-0.75, delta2=0.27, tau_min=0.03, tau_max=56.8. No GA refitting and no real Swift/BAT catalog data were required — these parameters were already validated against real data by the repository's prior work.

Every accepted light curve (i.e., one that passed the existing T90/S-N constraint filters in generate_GRBs()) shares a fixed-length time grid of 15,783 bins, determined by the instrument time resolution and the t_i/t_f window hardcoded in simulate_GRBs.py. This was confirmed empirically (wc -l across generated files) rather than assumed, and it is what makes a fixed-input-length CNN workable without padding or masking logic.

Two datasets were generated for this work: an initial N=3000 set used for the first full training run, and a larger N=10,000 set generated afterward for a follow-up run at higher label-count diversity and lower sampling noise in the rarer high-pulse-count classes.

2.3 Input representation

The CNN receives the lc column of each exported file — the background-subtracted, noise-added count-rate series, i.e. what an instrument would actually record — rather than the underlying pulse parameter list (lcN_lc_params.txt). This is deliberate: the network must learn to count from the same kind of signal a real analysis pipeline would have, not from privileged access to the generative parameters.

Each light curve is normalized independently by its own peak absolute value before being passed to the network:

x_normalized = x / max(|x|)

Per-LC amplitude is set by an independent random draw (A_max, sampled from the instrument's peak-count-rate distribution) that carries no information about pulse count. Without this normalization the network could partly key off absolute flux instead of waveform shape; normalizing removes that shortcut.

2.4 Network architecture

architecture_diagram.py renders the whole inference pipeline as a single schematic (architecture_diagram.png): an input light curve on the left, the five-block architecture described below in the middle, and the predicted count on the right, using a real example the model gets right (uniform_3000, true/predicted n_parent_pulses = 5, model runs_3000_p_uni, chosen for a matching in-distribution example rather than a mismatched natural-vs-uniform pairing).

Why PyTorch. A convolutional architecture with learnable filters and gradient-based training is not something scikit-learn (already a dependency of this repository) provides — it has no autodiff or convolution primitives — so a deep-learning framework was required regardless of which one. Between the two dominant options, PyTorch was chosen over TensorFlow/Keras for three practical reasons specific to this codebase: (1) its eager-execution model means the training loop in train.py is ordinary, readable Python — each line runs immediately and can be stepped through or printed mid-loop, which matters when debugging a repository that turned out to have this many environment/path issues (§3); (2) its Tensor API mirrors numpy closely, and this codebase already uses numpy throughout (avalanche.py, statistical_test.py), minimizing the new mental model needed to read dataset.py/model.py; (3) an official CPU-only wheel is distributed for Windows (--index-url https://download.pytorch.org/whl/cpu), matching the target machine (no GPU) without pulling in a much larger CUDA-enabled build.

The model (PulseCountCNN in model.py) is a compact 1D CNN:

Stage Layers Output channels ≈ Output length
Input — 1 15,783
Block 1 Conv1d(k=15, s=2, p=7) → BatchNorm1d → ReLU → MaxPool1d(4) 16 1,973
Block 2 Conv1d(k=9, s=2, p=4) → BatchNorm1d → ReLU → MaxPool1d(4) 32 246
Block 3 Conv1d(k=5, s=2, p=2) → BatchNorm1d → ReLU 64 123
Pooling AdaptiveAvgPool1d(1) 64 1
Head Flatten → Linear(64→32) → ReLU → Dropout(p=0.2) → Linear(32→1) 1 —

Each row of the table is a stage the data passes through, top to bottom. Output channels is the number of distinct pattern-detectors ("filters") running in parallel by the end of that stage — not a physical quantity, just more independent things the network is looking for at once. ≈ Output length is how many time-bins are left after that stage, which shrinks at every block as the network trades fine time resolution for a wider view of the signal.

In plain terms, each block is one round of "scan the signal for a pattern, then shrink it down" before the next block looks for bigger-picture patterns built from the previous ones. Taking Block 1, Conv1d(k=15, s=2, p=7) → BatchNorm1d → ReLU → MaxPool1d(4), layer by layer:

  • Conv1d(k=15, s=2, p=7) — a sliding-window filter. k=15 (kernel size) means each filter looks at 15 consecutive time-bins at once (roughly 1 second of data, since each bin is 0.064 s) to detect a local shape, such as the rise or decay of a pulse. s=2 (stride) means the window jumps forward 2 bins between looks instead of 1, which by itself already halves the output length. p=7 (padding) pads 7 zero-value bins onto each end of the input beforehand — pure bookkeeping so the output length comes out to a clean, predictable size; it doesn't add or remove information.
  • BatchNorm1d — rescales the filter's output numbers to stay in a well-behaved range. This is a standard trick for keeping training stable and fast; it doesn't change what shapes the network is capable of detecting, only how easily it learns to detect them.
  • ReLU — a simple on/off switch: keep a number if it's positive, otherwise set it to zero. Stacking many of these across layers is what lets the network build complex pattern-detectors out of simple ones.
  • MaxPool1d(4) — looks at every group of 4 consecutive values and keeps only the largest, discarding the other 3. This shrinks the sequence by another 4x and keeps whichever response was strongest nearby (loosely: "was there a strong version of this pattern somewhere in this neighborhood?"), which is what matters for counting peaks rather than knowing their exact position to the bin.

Combined, one block's stride-2 convolution and 4x max-pool shrink the sequence length by roughly 8x per block while growing the channel count — trading fine time resolution for more distinct, higher-level pattern-detectors. By the end of Block 3 the original 15,783-bin light curve has been reduced to a short sequence of 64 "was there a peak-like feature here" signals; global average pooling then collapses that down to one number per channel (64 numbers total, each summarizing that channel's average activity across the whole light curve), which the head (two small fully-connected layers) turns into the final predicted pulse count.

Global average pooling before the fully-connected head means the network's parameter count is independent of input sequence length — the same architecture accepts a different time grid (e.g. a different instrument resolution or window) without modification.

The raw scalar output is passed through softplus(x) + 1 before being returned. n_parent_pulses is bounded below at 1 by construction (avalanche.py redraws mu_s until nonzero), and this activation encodes that constraint directly in the architecture rather than relying on the loss function to discourage negative or sub-1 predictions during training.

Why these components, and not alternatives?

  • 1D convolution, not a fully-connected (dense) network. A light curve is a sequence in one dimension (time only), so a 1D convolution matches its structure directly, the way a 2D convolution matches an image's two spatial dimensions. Convolution is also translation-invariant by construction: a filter that has learned to recognize a pulse's rise/decay shape recognizes it the same way whether it occurs at t=2 s or t=80 s, without needing to see that shape at every possible position during training. A dense layer would need on the order of 15,783 × (hidden width) independent weights just for its first layer, with no such shared structure — impractical for a training set of a few thousand examples, and blind to the fact that "a pulse near the start" and "a pulse near the end" are the same underlying pattern.
  • BatchNorm1d after every convolution. Batch normalization is close to a default choice in modern CNNs because it stabilizes and speeds up training by keeping each layer's input distribution well-scaled. It matters somewhat more here because although each light curve is peak-normalized to its own maximum (§2.3), the shape of that normalized signal — how much of it sits near zero versus near the peak — still varies with pulse count and overlap, so re-centering activations layer-by-layer helps keep gradients well-behaved throughout training.
  • ReLU, not sigmoid/tanh. ReLU (max(0, x)) is the standard default nonlinearity for CNNs because, unlike sigmoid or tanh, its gradient doesn't shrink toward zero for large inputs ("vanishing gradients"), letting gradients propagate through multiple stacked conv blocks during backpropagation without stalling. It is also cheaper to compute, which matters when training on CPU.
  • MaxPool1d(4) inside the first two blocks. Two things motivate this rather than relying on the strided convolutions alone. First, practicality: the input is 15,783 bins long, and reducing it aggressively in the early blocks keeps the later, wider-channel layers cheap enough to train on CPU in reasonable time. Second, and more specific to this task: max-pooling adds a small amount of local shift-invariance — if a pulse's peak lands one or two bins to either side across two otherwise-similar light curves, max-pooling makes it more likely both produce a similar downstream signal, since what matters is whether a peak-like feature occurred nearby, not its exact bin.
  • AdaptiveAvgPool1d(1) at the end — average, not max, pooling. This is deliberately different from the max-pooling used earlier. By the last block, each of the 64 channels should ideally represent something like "how much of this pattern occurred across the whole light curve." Averaging that channel over time produces a value that grows with how often/strongly the pattern fired, which correlates with count. Maxing it would instead only answer "did this pattern occur at least once, anywhere," discarding exactly the information — how many times — the network is being asked to predict. This choice is also what makes the architecture input-length-agnostic (see above).
  • Dropout(p=0.2), applied only in the head. Placed in the small fully-connected head, not the convolutional feature extractor — the typical placement, since the dense layers have many parameters relative to the training set size (a few thousand light curves) and benefit most from this low-cost overfitting mitigation.
  • Adam optimizer, MSE loss (§2.5). Adam's adaptive per-parameter learning rates make it a robust default that needs little manual tuning, appropriate for a first working model rather than an already-tuned one. MSE is a standard, simple regression loss; a Poisson negative-log-likelihood loss would more closely match the label's actual Poisson-distributed nature and is a reasonable next experiment, but MSE was chosen here for simplicity, leaving the positivity constraint to the softplus output above rather than the loss function.

2.5 Training procedure

The model is trained as a regression problem (continuous output, rounded to the nearest integer only at evaluation time) using mean-squared-error loss against the integer label, optimized with Adam (default learning rate 1e-3). We chose regression over a fixed-class softmax because pulse count is an open-ended ordinal quantity with no natural upper bound to hardcode into a class list in advance.

Data are split 70% train / 15% validation / 15% test. The split is stratified by label when every class has at least two members (a requirement of scikit-learn's stratified splitting); it falls back to a plain random split otherwise, which matters for the sparsely populated high-pulse-count tail. The checkpoint saved for evaluation is the one with the lowest validation MAE across all training epochs, not the final epoch's weights, guarding against overfitting late in training.

2.6 Evaluation

The saved checkpoint is evaluated once, on the held-out test split (never seen during training or checkpoint selection). Three scalar metrics are reported: mean absolute error (MAE) after rounding predictions to the nearest integer; exact-match accuracy; and within-±1 accuracy (predictions off by at most one pulse). Two diagnostic figures are also produced, described in §2.7.

2.7 Validation figures

Two complementary histograms are generated by validate.py:

  1. True vs. predicted pulse-count distribution (pulse_count_distribution.png) — grouped bars comparing, for each label value k, how many test-set light curves truly had k parent pulses against how many the model predicted had k. This diagnoses distributional bias: a model that systematically under- or over-counts a particular range shows a visible mismatch here even if its average error looks acceptable.

§2.7's histograms are aggregate diagnostics; they don't show what an individual light curve actually looks like, or which specific examples the model gets right or wrong. prediction_examples.py closes that gap: for any trained run, it takes one held-out test example per distinct true n_parent_pulses value present in that run's test split (evenly spaced across the label range if there are more distinct values than the requested example count), plots each one's normalized input time series — literally the same array the CNN receives, peak-normalized, no time axis recovery needed since that's what the model was trained and is being diagnosed on — and titles each panel with True=k Pred=k' in green with a checkmark if they match, red with a cross if they don't (a status encoding, not decorative color — per the dataviz skill, correctness here is a state, so it also carries a symbol rather than relying on color alone). 3. Implementation issues resolved

These were pre-existing issues in the repository, unrelated to the CNN work itself, that blocked the pipeline and had to be fixed first.

3.1 user variable collision in simulate_GRBs.py

simulate_GRBs.py sets user='external_user' so that it resolves file paths relative to the repository instead of a hardcoded path belonging to one of the original authors. It also executes from statistical_test import *, and statistical_test.py independently defined its own module-level variable also named user (user={'bach', 'gravity'}, used only for that file's internal sys.path setup). The wildcard import silently overwrote simulate_GRBs.py's user, so the if user=='external_user': branch was never taken at runtime, and the script silently fell through to a branch that ignored config.ini and used the wrong output path.

Resolution: renamed the internal variable in statistical_test.py to _user (a leading underscore is excluded from import * by Python convention). Nothing else in the codebase referenced the old name, so this is a pure namespace-isolation fix.

3.2 n_sig_pulses computation is broken upstream

Enabling generate_GRBs(..., test_pulse_distr=True) (required to compute n_sig_pulses) raises AttributeError: 'LC' object has no attribute '_ampl' inside count_significative_pulses_ver2(). The referenced attribute is dead code in avalanche.py — commented out (# self._ampl = ampl, line 481), left over from an amplitude-scaling scheme that was superseded by the current per-pulse A_max sampling approach. Reconstructing an equivalent scaling factor would require assumptions about intent that cannot be verified from the current code, so this was left unfixed and out of scope; n_parent_pulses (§2.1) was used instead. test_pulse_distr remains False.

3.3 PyTorch installed into the wrong Python interpreter

conda run -n pygad3 pip install torch reported a successful install, but import torch subsequently failed inside the same environment. The pygad3 environment's own interpreter had no pip module at all (python -m pip → No module named pip), so the bare pip command resolved to a different Python installation found earlier on PATH (a Windows Store Python) and installed torch there instead.

Resolution: conda install -n pygad3 pip to give the environment its own package manager, then conda run -n pygad3 python -m pip install torch --index-url https://download.pytorch.org/whl/cpu, which ties the install explicitly to the target interpreter rather than trusting PATH resolution.

3.4 OpenMP runtime collision on import

With torch correctly installed, importing it alongside numpy raised OMP: Error #15: Initializing libomp.dll, but found libiomp5md.dll already initialized — a known Windows/conda packaging conflict between torch's bundled OpenMP runtime and the one numpy's MKL backend loads.

Resolution: os.environ.setdefault('KMP_DUPLICATE_LIB_OK', 'TRUE') is set at the top of train.py and validate.py, before import torch. This is the standard workaround for this conflict; it is safe in this context because training and validation run single-process on CPU with no dependence on strict OpenMP thread-affinity guarantees.

4. Code organization

4.1 Files responsible for light-curve generation

These are pre-existing repository files, not written for this work; this section describes what each one does in the generation pipeline, as context for the changes listed in §4.2 below.

  • lc_pulse_avalanche/avalanche.py — the physical simulator core. Defines the LC class, whose generate_avalanche() method implements the SS96 stochastic process itself: draws the Poisson-distributed number of parent pulses, recursively spawns each parent's cascade of child pulses (_rec_gen_pulse()), sums every pulse into a raw light curve, and applies the chosen instrument's response — effective area, background level, and a Swift- or BATSE-specific noise model — to produce the final observed count-rate series. This file has no awareness of output files, labels, or command-line arguments; it is a pure simulation library consumed by the layer below.
  • statistical_test/statistical_test.py — despite its name (it is the repository's general-purpose analysis module, used for both real and simulated data), the pieces relevant to generation are: the GRB class, a plain container holding one light curve's time series plus its metadata (T90, pulse counts, file path, etc.); generate_GRBs(), the higher-level loop that repeatedly instantiates LC, applies the T90 and signal-to-noise constraint filters that decide whether a simulated burst is "acceptable" (apply_constraints()), and wraps each accepted one in a GRB object; and export_grb() / export_lc_params(), the two functions that serialize an accepted GRB to the lcN.txt and lcN_lc_params.txt files respectively.
  • lc_pulse_avalanche/simulate_GRBs.py — the command-line entry point that orchestrates the two files above. It reads config.ini, resolves the instrument-specific physical constants (effective area, background level, S/N threshold) from the dictionaries defined in statistical_test.py, calls generate_GRBs() with the requested parameters and N_grb target, and creates the timestamped simulated_LCs/<timestamp>/ output directory via create_dir().
  • lc_pulse_avalanche/config.ini — a plain key = value parameter file, not code: selects the instrument (swift/batse), the number of light curves to generate (N_grb), and the 7 SS96 model parameters. It carries no logic of its own; simulate_GRBs.py's read_values() function parses it into a plain dict.

4.4 Live progress reporting

Both light-curve generation and training can run for tens of minutes to hours at the larger dataset sizes in §7. Two issues had to be fixed before either showed any progress before completion:

  • No progress output at all during generation. generate_GRBs()'s main loop (§4.1) previously printed nothing until every requested light curve was done. It now prints an in-place-updating [simulate] cnt/N_grb line (a carriage-return update — \r plus end='', right-padded to N_grb's digit width — not one line per LC) every time a light curve is accepted, followed by a final newline once generation finishes so subsequent output starts cleanly. train.py similarly prints a batch/n_batches line four times per epoch, in addition to its existing per-epoch summary.
  • Output buffering. By default, Python buffers stdout in blocks (rather than flushing per line) whenever it isn't connected to an interactive terminal. sys.stdout.reconfigure(line_buffering=True), added near the top of simulate_GRBs.py, train.py, and validate.py, forces a flush after every line/carriage-return so the progress above updates immediately in an interactive terminal you are actively running the command in (§5.2) — this is the setup to use if you want to watch progress live.

This does not reliably help when the process is instead launched as a detached background job whose output is redirected to a log file (e.g. via a job scheduler, or Start-Process/&-backgrounding) — in that setup, something in the redirection/capture path can still withhold output until the process exits regardless of the script's own flushing, and the exact behavior depends on how the backgrounding is done. If you need to monitor a background run, prefer watching the growing count of lcN.txt files in the output directory over tailing a redirected log.

On-screen (graphical) progress, opt-in and separate from the terminal output above:

  • During generation (config.ini: gui_progress = true): simulate_GRBs.py's LiveGenerationProgress opens a small window with a horizontal bar that fills from 0 to N_grb as light curves are accepted, wired via generate_GRBs()'s new progress_callback parameter. The window stays open (blocking, via plt.show()) once generation finishes, so the final "100% done" state is visible until you close it.
  • During training (train.py --live-plot): LiveTrainingPlot opens a window with two side-by-side subplots — train/val loss, and val MAE/exact-match accuracy — each updating with one new point per epoch. Also stays open (blocking) after training completes, showing the full curve for review.
  • Both are opt-in (off by default) because they need an actual display — running them via a background/redirected process, or on a machine with no GUI toolkit available, would either show nothing or fail outright. Both wrap their window-creation in try/except: if no display is available, they print a warning and the run continues normally with only the terminal progress from above — a missing display is a degraded experience, not a crash.
  • Both use a QtAgg-backed interactive matplotlib window (confirmed available in this project's environment, with tkinter as a fallback toolkit); no new dependency was added; the same matplotlib already used for the histograms elsewhere in this project.

4.5 Light-curve visualization (plot_lcs.py), and two findings from building it

lc_pulse_avalanche/plot_lcs.py (new) plots each lcN.txt's observed time series and saves lcN_plot.png alongside the existing .txt files in that run's directory. Usage:

python plot_lcs.py                                    # plots the most recent run
python plot_lcs.py --run-dir ../simulated_LCs/<timestamp>
python plot_lcs.py --limit 20                          # only plot the first N (large runs)

Building this required the simulator to record information it previously discarded: avalanche.py's _lc_params entries (§2.1, §4.1) gained two new fields — is_parent (True for the mu_s spontaneous pulses, False for anything spawned by _rec_gen_pulse()) and parent_id (the index, in generation order, of each pulse's immediate progenitor; None/-1 for top-level parents). export_lc_params() now writes both as extra columns in lcN_lc_params.txt. plot_lcs.py uses these to mark parent pulses (numbered, red) and child pulses (small, muted) at each pulse's peak time, placed on the observed curve at the nearest time bin. (Datasets generated before this change lack these two columns; plot_lcs.py detects this and skips the markers rather than erroring.)

Building and using this tool surfaced two things worth recording:

Finding 1 — the recursion's time bookkeeping is correct, not the bug the code comments worried it might be. _rec_gen_pulse()'s docstring (avalanche.py:201-220) contains a debate, apparently between the original authors, over whether each pulse's time delay (t_shift) is correctly accumulated across generations or incorrectly reset relative to just the immediate parent. This was checked empirically rather than by reading code alone: across all 22,609 child pulses in a 20-LC test batch, every single one had a t_delay strictly later than its immediate progenitor's — zero violations. The recursion does correctly carry the cumulative absolute time forward through arbitrarily many generations, exactly as the comment concludes it should. One direct consequence, visible once plot_lcs.py could show it: a long-lived cascade (one where tau shrinks slowly across generations before finally dying out) can legitimately drift its descendants far in time from their own originating parent — visually, a child pulse can end up closer to a different parent's cluster than its own. Combined with each pulse's amplitude being drawn independently of its generation depth (so a late descendant can be brighter than its own parent), this fully explains why a "child" marker can appear somewhere unintuitive without any bug being involved.

Finding 2 — n_cut=2500 (simulate_GRBs.py:155) is a real, frequently-hit constraint, not a theoretical edge case. This cap on total pulses is shared across an entire light curve's avalanche (every parent's cascade combined), checked via if self._n_pulses < self._n_cut before extending any branch further. Tested on 100 freshly generated LCs: 13 (13%) hit or exceeded the cap, with values clustering tightly just above 2,500 (2507-2535) — confirming genuine truncation rather than coincidence — and another 5 (18 total) were within striking distance (≥2,000). Mean n_pls across the 100 was ~699, but the distribution is heavily right-skewed: most light curves have well under 100 total pulses, while a minority spike into the thousands. Because the budget is shared globally rather than per-parent, one prolific family can truncate a different parent's cascade within the same light curve — a real, if secondary, source of the kind of "why does this family look artificially sparse" discrepancy discussed above. This has not been changed; it is the existing, working behavior of a repository file not otherwise touched by this project, documented here because it was surfaced by building the visualization tool, not because it was identified as something requiring a fix.

Observation 3 (qualitative, not yet quantitatively verified) — dense clusters of child pulses tend to visually coincide with what a human would call "a peak," more so than the is_parent-tagged pulse itself. Reviewing plot_lcs.py's output revealed that the region a human eye would identify as the light curve's dominant bump is often where many child pulses (from one or several families) pile up in time, rather than necessarily sitting exactly on a numbered parent marker. This connects directly to §2.1's original justification for using n_parent_pulses as a proxy for "number of visually distinguishable peaks": that argument assumed each parent's cascade produces roughly one bump centered near the parent. This observation suggests the correspondence may be less clean than that — a human counting bumps by eye could plausibly count cluster regions (which can pool children from multiple families, per Finding 1's time-drift, or split one family's cascade across a wide span) rather than parents one-for-one. This has not been quantified — doing so would mean comparing n_parent_pulses against an actual independent peak-counting method (e.g., a real peak-finding algorithm run on the observed curve, which is also what the broken n_sig_pulses/MEPSA-style path in §3.2 was originally meant to provide) rather than against visual impression alone. Until that comparison exists, this is a flagged, plausible limitation on §2.1's proxy argument, not a confirmed discrepancy — recorded here because it surfaced directly from building the visualization tool, the same way Findings 1 and 2 did.

Finding 4 — a genuine contradiction between two comments in the pre-existing codebase about what units the lc column is in. avalanche.py:506 states explicitly: "For Swift, the variable _plot_lc contains the COUNT RATES (and not the counts!)". statistical_test.py:3185 says the opposite when constructing the GRB object: `counts=lc._plot_lc,

these are COUNTS (not count rates!)`. Tracing the actual computation

resolves this: self._model_rate = self._model / self._res (counts divided by the time resolution) is what feeds _plot_lc for Swift, which is a rate (counts/second) by construction, not a count — avalanche.py's comment is correct, and statistical_test.py's is wrong (most likely a copy-paste artifact from the BATSE branch immediately above it, where _plot_lc genuinely is in counts). This means plot_lcs.py's y-axis was mislabeled "Counts" and has been corrected to "Count rate [cnt/s]"; no other part of this project's pipeline treats the lc column's units in a way that this affects (the CNN's input is peak-normalized per light curve, §2.3, so it's insensitive to which unit convention the raw signal is in).

4.6 How does the number of parent pulses actually change the light curve?

Comparing real generated examples across n_parent_pulses = 1, 2, 3, and 4 (simulated_LCs/2026-07-22_13-57-00/lc*_plot.png and simulated_LCs/2026-07-21_09-13-51/lc9_plot.png) makes the effect concrete rather than abstract:

  • More parents → more distinct active regions ("bumps"), spread further across the light curve. A 1-parent light curve is a single cluster of activity around one point in time. By 4 parents (lc9.txt, count rate peaking at ~28 cnt/s around t≈130s), the light curve shows visibly separate clusters around t≈0-20s, t≈60-90s, t≈100-160s, and t≈220-260s — each traceable to a different parent's cascade (§2.1, §4.5).
  • The active window widens, but the total light curve length doesn't. Every light curve, regardless of n_parent_pulses, is generated on the same fixed -10s to +1000s grid (§2.2) — what changes is how much of the early part of that window (roughly the first 0-300s here) contains signal versus pure background noise. More parents means a longer stretch of real activity, not a longer file.
  • Peak brightness tends to increase with more parents, but not linearly or reliably — each pulse's amplitude is drawn independently (§2.4, §7.10's norm discussion), so a 4-parent light curve has more chances for a high-amplitude pulse to occur, but a 1-parent light curve can still, by chance, be brighter than a 4-parent one. Compare lc9.txt's peak (~28 cnt/s, 4 parents) against typical 2-3 parent examples in the same batch, which mostly peak lower — a tendency, not a guarantee.
  • The relationship is not "N cleanly-separated bumps for N parents." Per §4.5's Findings 1 and Observation 3, cascades can drift in time and interleave with each other, and dense child-pulse clusters often read as "one visual peak" regardless of how many parents contributed to them. So while the general trend (more parents → busier, longer-active light curve) is visually obvious and consistent across every example examined, a precise one-to-one "count the bumps, get n_parent_pulses" reading is not reliable — which is exactly the difficulty the CNN in this project is up against (§7.2-§7.11).

This is also the mechanism the uni dataset (§7.11) exploits: since raising mu0 shifts the typical number of parents upward (§7, this methodology also underlies how generate_uniform_bins.py targets each bin), it also shifts the typical light curve toward "busier, more spread-out" — the visual pattern above, not just an abstract label change.

6. Expected effect of a larger dataset (N=10,000)

A second dataset of N=10,000 light curves was generated (same instrument and parameters as §2.2) alongside this report, to be trained on separately. Ahead of those results, it is worth being explicit about what scaling the dataset by roughly 3.3x should and should not be expected to change, based on general supervised-learning behavior rather than results specific to this problem:

  • The label distribution keeps the same shape. mu0=1.16 is fixed across every generation run, so the underlying Poisson-shaped label distribution (mostly 1-2 parent pulses, tailing off sharply by 5-6) doesn't change with N — a larger dataset gives more absolute examples of each class, not a more balanced proportion of them. The rare high-count tail (5, 6+ parents) remains a small fraction of the dataset either way.
  • The rare classes should benefit disproportionately. A 50-LC pilot sample showed classes like "5 parents" or "6 parents" with single-digit example counts at N≈3000-scale — too few for the model to learn a reliable pattern for, and too few in the test split to measure accuracy on with any confidence. At N=10,000 those same rare classes scale up roughly proportionally in absolute count, which should improve both the model's ability to learn them and the reliability of the reported per-class accuracy. This is where the largest qualitative improvement is expected — more than in the already well-populated 1-2 parent classes.
  • Held-out metrics should become less noisy. MAE and accuracy computed on a 15%-of-3000 ≈ 450-example test set carry more sampling variance than the same metrics on a 15%-of-10,000 ≈ 1,500-example test set. Part of any difference between the two runs' reported numbers should be attributed to this effect rather than assumed to be a genuinely better model.
  • More optimizer steps per epoch. With a fixed batch size, one epoch over 10,000 light curves is ~3.3x more gradient updates than one epoch over 3000. Comparing training curves between the two runs should account for this — it is not purely a "more data" effect.
  • Diminishing returns should be expected past some point. This is a deliberately compact model (§2.4) relative to the input size; more data mostly helps a model like this by reducing overfitting/variance on classes it can already represent, rather than unlocking qualitatively new capacity. If accuracy on the rare tail is still poor at N=10,000, that would point toward a class-imbalance problem — better addressed by oversampling rare classes, or varying mu0 across generation runs to deliberately produce more high-count examples — rather than a needs-more-data problem, and would be worth investigating before simply scaling N further.
  • Generation and training time scale roughly linearly with N. Light-curve generation took approximately 20 minutes for N=3000 on the development machine, so N=10,000 was expected to take on the order of an hour; each training epoch likewise takes roughly 3.3x longer at N=10,000 than at N=3000 for the same batch size.

The actual comparative metrics and both validation figures for the N=10,000 run will be appended here once training on it completes.

7. Results

Training configurations tested. Every run directory follows runs_{N}_{loss}_{weighting}, where loss is mse or p (Poisson NLL, §2.5) and weighting is one of four strategies for handling the class imbalance in n_parent_pulses (§7.3):

  • unw (unweighted) — the natural, Poisson-imbalanced dataset, plain random sampling, no reweighting of any kind.
  • wgt (weighted) — the same natural dataset, but training batches are drawn via WeightedRandomSampler with inverse-class-frequency weights (§7.6) — no data is removed, rare examples are just shown more often.
  • cap (capped) — the same natural dataset, but undersampled to at most 1,000 examples per class before training (§7.10) — majority-class data is permanently discarded; rare classes are untouched; sampling during training is then plain/unweighted on this smaller set.
  • uni (uniform) — not a resampling of the natural dataset at all, but a separately-generated dataset built by running the simulator at a different mu0 per target bin and harvesting only the matches (§7.11), every other Bazzanini-calibrated parameter held fixed. Capped below the full 1-10 range originally planned, and by a different amount at each size, because the same per-bin cost growth documented in §9's diagnostic keeps biting harder the more matches are needed per bin: 300 light curves for each of bins 1-8 at N=3,000 (2,400 total), but only 1,000 light curves for each of bins 1-7 at N=10,000 (7,000 total) — bin 8 was dropped at the larger size after its cost trend (bin 7 alone slowed to roughly a quarter of bins 1-6's pace) made finishing it impractical against the deadline.

The full label distribution generated at N=3,000 was:

The trained model reached a held-out test MAE of 0.633, exact-match accuracy of 46.2%, and within-±1 accuracy of 92.2%. Those top-line numbers look reasonable in isolation, but the two validation figures (runs_3000_mse_unw/pulse_count_distribution.png, runs_3000_mse_unw/prediction_error_histogram.png) show what's actually happening underneath them: the model essentially stopped predicting anything other than 1 or 2. The true test-set distribution has real mass out to 6; the predicted distribution has none above 2 — every light curve truly labeled 3, 4, 5, or 6 was predicted as 1 or 2. This is visible directly in the error histogram: the negative-error bars (predictions falling short of the true count) account for essentially the entire non-zero-error mass, with almost no over-prediction.

This also explains the apparent tension between the metrics: MAE and within-±1 accuracy look good mainly because 77% of the test set truly has only 1-2 parent pulses, so "always guess 1 or 2" is a low-regret strategy under a mean-error metric even though it never engages with the actual counting task for a quarter of the data. Exact-match accuracy (46.2%) is the metric least flattered by this behavior, and it's correspondingly the weakest number. The per-epoch training history (runs_3000_mse_unw/history.csv) is consistent with this reading: training loss fell steadily for all 25 epochs (0.924 → 0.807), while validation accuracy barely moved (0.362 → 0.420) and plateaued early — the network kept improving its ability to fit the dominant classes rather than learning to discriminate the rare ones.

7.3 Why this happened

Four factors plausibly contributed, roughly in order of expected impact:

  1. Class imbalance. Only 8 of 3,000 light curves (0.3%) have 6 parent pulses; only 39 (1.3%) have 5. After a 15% test split, that's ~1 and ~6 examples respectively — too few for the model to ever receive a strong, consistent training signal for those classes, and too few to reliably measure performance on them even if it had learned something.
  2. MSE regression pulls toward the conditional mean. With squared-error loss, the gradient contribution from the numerous, easy 1-2-pulse examples dominates the total loss simply by weight of numbers, pushing the model toward always predicting close to the population mean (≈1.9) rather than risking a confident but occasionally wrong extreme prediction. This is a well-known failure mode of plain MSE regression on imbalanced/skewed count data, independent of network architecture.
  3. Possible intrinsic signal ambiguity. Parent-pulse cascades can overlap heavily in time, especially for small tau draws (§2.4 of the underlying SS96 model allows child pulses within alpha * tau0 of their parent). Two, three, or more overlapping cascades can plausibly blend into a light curve that doesn't look very different, post-noise, from one with fewer, cleaner cascades. Some part of the ceiling here may be information the noisy observed signal genuinely does not preserve cleanly — not solely a data-quantity or loss-function problem. This cannot be distinguished from factors 1-2 without further experiments (§7.5).
  4. Model capacity and information loss from global pooling. The network is deliberately compact (§2.4), and global average pooling discards all positional information before the final prediction — the head sees only "how active was each channel on average," not "how many separate activation events occurred." That representation may simply cap out before it can resolve fine-grained count differences in the tail.

7.4 Why real Swift/BAT light curves should resemble these simulations, despite using no real catalog data directly

It's worth being precise about why this pipeline can claim any resemblance to real data at all, since the immediate generation step (§2.2) never touches a real GRB. The seven SS96 parameters used (mu=1.34, mu0=1.16, alpha=2.53, delta1=-0.75, delta2=0.27, tau_min=0.03, tau_max=56.8) are not arbitrary or hand-picked — they are the published output of a genetic-algorithm optimization (the geneticgrbs.py / v36 (bazzanini+24 paper) fit already present in this repository) that searched parameter space to minimize the statistical distance between simulated and real Swift/BAT light curves — matched on ensemble properties such as peak-count distributions, autocorrelation function shape, and T90 distributions, against the real Swift/BAT catalog. That fitting step is where the real data enters the pipeline; we did not have to touch the catalog again downstream because its statistical fingerprint is already compressed into those seven numbers. Drawing new synthetic light curves from that calibrated regime therefore reproduces the same population-level statistics as real Swift/BAT bursts, by construction — that is the entire purpose of the original calibration, and it's why no GA refitting or real-catalog access was needed for this work (as established earlier in this conversation).

This resemblance, however, is real only at the ensemble/statistical level, and it is important not to overstate it:

  • It says nothing about whether any individual simulated light curve resembles any individual real GRB — only that the two populations' aggregate statistics (the ones the GA optimization targeted) match.
  • Most importantly for this specific model: n_parent_pulses has no real-data counterpart. It is a latent quantity internal to the SS96 generative process — a real GRB has no directly observable "number of independent trigger events," only an observed light curve. There is no way to obtain a ground-truth n_parent_pulses label for a real Swift burst to check the trained model against; §2.1's physical argument for why it's a reasonable proxy for "visually distinguishable peaks" is exactly that — an argument, not something verified against real data here. This is the most important caveat on the entire exercise and is restated in §8.
  • The calibration is specific to the ensemble Swift/BAT was fit against (long GRBs, the t90_threshold/sn_threshold selection already baked into generate_GRBs(), §2.2's constraint filters). It does not guarantee the same closeness for GRB subpopulations outside that selection.

7.5 What can be done about the mode-collapse behavior

In roughly increasing order of implementation effort:

  • Stratified/weighted batch sampling. Currently only the train/val/test split is stratified (§2.5); minibatches themselves are drawn uniformly at random, so a batch is still dominated by 1-2-pulse examples. A weighted sampler (e.g. torch.utils.data.WeightedRandomSampler, inverse-frequency weights) would give rare classes equal presence within every batch, directly countering factor 1 in §7.3 without needing more data.
  • A loss function suited to imbalanced count data. Plain MSE is what drives the mean-seeking behavior in §7.3. A Poisson negative-log-likelihood loss would match the label's actual generating distribution; alternatively, per-class-weighted MSE (upweighting rare classes' contribution to the loss) is a smaller change with a similar effect.
  • Targeted data generation. Rather than only increasing N at the existing mu0=1.16, generating additional batches at deliberately higher mu0 would produce many more naturally-occurring high-pulse-count examples to mix into training, directly enriching the rare classes instead of waiting for them to accumulate at their natural (low) rate.
  • More data at the existing distribution — the N=10,000/20,000 runs already underway. Expected to help (§6) but, per §7.3's point 3, cannot by itself resolve the issue if part of the ceiling is genuine information loss in the observed signal rather than a shortage of examples — this is exactly what comparing 3,000 vs. 10,000 vs. 20,000 is designed to reveal (§7.6): if the tail accuracy improves substantially with N, the bottleneck is data/imbalance; if it stays flat, the bottleneck is more likely information loss or model capacity.
  • Architecture changes, if the above don't resolve it: replacing global average pooling with a representation that retains some positional/count structure (e.g. summing per-channel activations above a learned threshold, closer to a soft peak-counting operation, rather than averaging), or simply a deeper/wider network — though this is the most expensive lever to pull and is not indicated as the first fix given factors 1-2 are cheaper to rule out first.

7.6 Chosen fix: balanced sampling + Poisson loss (implemented)

We evaluated the §7.5 options against three criteria: (1) can it be tested immediately, without waiting on new data generation; (2) does it directly target the mechanisms identified in §7.3, rather than just working around them; (3) implementation cost. Targeted data generation and "more data" both leave the core mechanism untouched — they supply more examples but don't change how those examples are weighted during training (§7.3, points 1-2) — and architecture changes are the most expensive option and, per §7.5, not indicated as a first move. That leaves the two cheapest, most directly targeted fixes: weighted batch sampling and a count-appropriate loss. These are not mutually exclusive and address different mechanisms (representation during training vs. how errors are penalized), so both were implemented together:

  1. Balanced sampling. train.py's new make_train_loader() builds training batches with torch.utils.data.WeightedRandomSampler, weighting each example by the inverse frequency of its class (1 / count(class)), sampled with replacement. Every training batch now has, in expectation, roughly equal representation across n_parent_pulses values, rather than being dominated by the 1-2 classes as in §7.2. Validation and test loaders are deliberately left uniform (unweighted) — evaluation must reflect the real, imbalanced population, not the rebalanced training distribution, or the reported metrics would no longer mean "performance on realistic data."
  2. Poisson loss. The training loss now defaults to nn.PoissonNLLLoss(log_input=False, full=True) in place of nn.MSELoss(). Since the model's output (softplus(x) + 1, §2.4) is already a positive rate rather than a log-rate, log_input=False is required; full=True adds the Stirling-approximation term so the printed loss is interpretable as an approximate negative log-likelihood, though it does not change the gradient with respect to the prediction.

Both are exposed as CLI flags (--sampler {uniform,balanced}, --loss {mse,poisson}, both defaulting to the new, fixed behavior), so §7.2's original configuration remains reproducible via --sampler uniform --loss mse for comparison.

To isolate the effect of this fix from the effect of more data, it was first re-run on the same N=3,000 dataset with the same train/val/test split (--seed 42 unchanged from §7.2) — only --sampler/--loss changed — saved to runs_3000_p_wgt/ rather than overwriting the runs_3000_mse_unw/ baseline. That last point is the important one: classes 4, 5, and 6 have only 23, 6, and 1 test examples respectively (and correspondingly few in training — roughly 110, 27, 6 before the split). Inverse-frequency weighting makes the sampler present those few examples more often, but with replacement — it cannot manufacture information that isn't there. Training on 25 repeated views of the same ~6 class-5 light curves is a recipe for memorizing those specific 6, not for learning a generalizable "6 parent pulses" pattern; 25 epochs of oversampling a 6-example class is a fundamentally different (and much weaker) regime than 25 epochs over a genuinely larger class-5 sample. This directly matches the concern raised in §7.3, point 1: the fix addresses how the existing rare examples are weighted, but not the fact that there are too few of them to learn from in the first place. It is a real, working answer to "is the model taking a shortcut because of how it's trained" (yes, and this partially corrects it for classes with enough examples to reweight usefully, i.e. class 3), but not a substitute for §7.7's actual test: whether more raw data resolves the classes this fix could not touch.

Given this, the fix is being kept enabled by default for the N=10,000 and N=20,000 runs below (more examples per rare class make oversampling more meaningful, and there is no reason to expect the uniform-sampling/MSE mode-collapse to be better at larger N), but §7.7's comparison should be read as "more data, with the fix already applied" rather than an isolated test of data quantity alone — the two effects are intentionally stacked at that point, having already isolated the fix's own effect above.

Either way, this is a genuine reason to trust the per-class breakdown over aggregate exact-match accuracy when judging whether scaling data is helping — the aggregate number moved in a direction that would look like "getting worse" while the class this experiment was actually targeting (3) demonstrably improved.

Bottom line for the question this comparison was designed to answer: the evidence is genuinely mixed, not a single clean verdict. Part of the tail (class 3, plausibly class 4 with more data) responds to more data — supporting the imbalance/data-quantity explanation. Part of it (classes 5-7) shows no response across a 3.3x increase in N — consistent with those specific classes needing substantially more data than tested here, rather than necessarily an information-loss ceiling; nothing here rules out data quantity as the eventual fix for classes 5-7, only that 10,000 isn't enough yet. Whether N=20,000 is worth running to test that further is an open decision (§7.1) — that run is currently on hold.

7.8 Discussion: what the two comparisons tell us together, and what needs to change

Run in isolation, neither §7.6 nor §7.7 would be conclusive. Read together, they let us attribute which rare classes are failing for which reason, rather than treating "the model is bad at rare classes" as one undifferentiated problem.

What the two comparisons tell us:

  • Class 3 is a data-quantity problem, and it is solved by scale. 73→259 test examples (3k→10k) took its accuracy from 9.6%→18.5% — roughly doubling in proportion to roughly doubling the data. This is the clean, unambiguous result of this whole exercise: more data works, when there is a realistic amount of it to add.
  • Classes 5, 6, and 7 are not solved by a 3.3x increase in data — flat 0% at both dataset sizes, because even 10,000 total light curves yields only 21, 3, and 1 test examples for them respectively. That is not evidence that "scale doesn't work" for these classes; it is evidence that 3.3x more of an already-tiny number is still a tiny number. Given the fixed Poisson rate, bringing class 7 to where class 3 already sits (~250 examples) would require on the order of 250/0.0006 ≈ 400,000+ light curves at this mu0 — scale alone is not a practical fix for these classes at the rates tested here.
  • Class 4 is genuinely ambiguous — 0.0%→1.4% despite tripling its example count (23→72). It neither clearly responds the way class 3 did nor stays as flatly dead as classes 5-7. This is the class an N=20,000 run would be most informative about.
  • The §7.6 fix is necessary but not sufficient, and its effect on the dominant classes is uneven across dataset sizes. It is what let class 3 improve at all — the unfixed baseline predicted nothing above 2, ever — but class 1's accuracy moved non-monotonically across the three runs (35.0% → 51.9% → 35.6%, baseline → 3k-fix → 10k-fix), which is a sign the reweighting mechanism itself behaves somewhat differently at different dataset sizes, not simply "more data, uniformly better."
  • Aggregate metrics (MAE, exact-match accuracy) are actively misleading here. Both got slightly worse from the 3k-fix run to the 10k-fix run, even though the class this whole experiment was targeting (3) clearly improved. Judging "did this help" from the aggregate number alone would give the wrong answer — the per-class breakdown is not optional context, it is the load-bearing evidence.

What needs to change to improve accuracy, in priority order (based on what the data actually showed, not what seemed promising before testing):

  1. Targeted data generation for classes 5-7, not just more of the same distribution. Since mu0=1.16 is fixed, every additional light curve is disproportionately a 1 or 2. Generating separate batches at a deliberately higher mu0 — to naturally produce far more 5/6/7-pulse bursts — and mixing them into training is the direct fix; waiting for uniform-distribution scale to do it "naturally" is not practical at the rates involved (previous point).
  2. Repeat runs across multiple seeds before trusting any single comparison further. The class-1 non-monotonicity above is exactly the kind of thing that could be run-to-run noise rather than a real effect of dataset size — every result so far is a single seed, single split (§8), so we currently cannot tell which it is.
  3. Reconsider the strength of the reweighting, not just whether to use it. Full inverse-class-frequency weighting may be over-correcting for the dominant classes — class 2's accuracy dropped from 87.8% (baseline) to 54.9% (3k-fix) and only partially recovered at 10k (60.5%), never approaching its baseline level. A softer scheme, e.g. weighting by 1/sqrt(count) instead of 1/count, would rebalance rare classes less aggressively and might reduce this collateral damage while still helping class 3.
  4. Architecture changes become worth trying specifically once class 4's ambiguous result is resolved. If class 4 does not clearly respond to a future data increase either, that would be evidence that global average pooling (which discards positional/count information, §2.4) is capping what is learnable regardless of data or reweighting — at that point, a representation closer to "count distinct activations" rather than "average activation" is the more promising lever, not more data.
  5. N=20,000 (or targeted generation instead of it, per point 1) is the direct next test for whether class 4 keeps responding to scale the way class 3 did, or plateaus like classes 5-7 — currently on hold pending a decision on which of these is the better use of that time.

7.10 Isolating the fix's two components: sampler vs. loss, plus a third strategy

  2. Undersampling to a cap doesn't fix mode collapse — it just relocates it. It also comes with the same trade-off in a sharper form: class 1 was sacrificed almost entirely to get class 3's gain, and classes 4+ (never brought to parity, still only 511/125/15/6/1 raw examples) saw no benefit at all. Whether this generalizes — e.g. would capping at a size that also equalizes class 4 unlock it too, at the cost of even more of classes 1-3 — is a direct, concrete next experiment this result motivates, not yet run.

8. Limitations

  • n_sig_pulses remains broken upstream (§3.2) and unused; only n_parent_pulses is a reliable label from this pipeline at present.
  • The model is trained on a single, fixed instrument/parameter regime (Swift v36-calibrated). It has no basis for generalizing to BATSE light curves, or to a different SS96 parameter set, without retraining on data generated under those settings.
  • Each reported run reflects a single train/val/test split and a single random seed; metrics are not averaged over repeated splits or seeds.
  • The model cannot be directly verified against real GRB light curves. n_parent_pulses is a latent quantity — it exists only because the synthetic pipeline knows exactly how many pulses it drew from the SS96 avalanche model when generating a light curve. No real catalog (Swift/ BAT, BATSE) records a "true number of parent pulses" for an observed burst; it is not a measured physical quantity, it is an artifact of this specific generative model, so there is no ground-truth label to check a real-light-curve prediction against. The closest available proxy is independent peak-counting: genetic_algorithm/geneticgrbs.py already references precomputed MEPSA significant-peak counts for real Swift/BAT bursts (mepsa_out_file_list) and statistical_test.py has a matching n_sig_pulses field (currently broken upstream, above) — comparing the CNN's prediction on a real light curve to MEPSA's peak count would be a consistency check between two different pulse-counting methods, not ground-truth verification, since MEPSA counts only peaks above a detection threshold while the CNN was trained to recover the underlying generative count (including overlapping/sub-threshold pulses a peak-finder would miss) — agreement wouldn't prove correctness and disagreement wouldn't prove error. This is moot for now regardless: both the real catalog and the precomputed MEPSA files are hardcoded to remote server paths (/astrodata/guidorzi/..., /beegfs/mbulla/..., §4.1) that don't exist on this machine, so pursuing this would first require acquiring that data. lc_gallery.py (§10.3) offers a much weaker, purely visual substitute: representative synthetic light curves by pulse count, for eyeballing rough morphological similarity against a real burst, which is not a validation method.

9. A second parameter regime: mu0=10

Everything in §7 uses the Bazzanini-calibrated Swift/BAT value mu0=1.16 (config.ini), which sets the Poisson-distributed number of parent pulses per light curve to a mode of 1 and a heavy right tail. mu0 is the only SS96 parameter that controls n_parent_pulses (§2.1, §7 overview) — the other six (mu, alpha, delta1, delta2, tau_min, tau_max) shape pulse shape and timing, not count. To see how the whole investigation's findings change under a distribution centered somewhere else, mu0 was raised to 10 (config.ini, old value commented out rather than deleted) and a fresh 3,000- and 10,000-LC dataset generated under it, then run through the same training conditions as §7.

Scope reduction (later completed). Generation and training at N=10,000 under mu0=10 proved far more expensive than anticipated (see cost diagnostic below), and this track was initially run against a hard deadline — only the Poisson-loss conditions (unw, wgt, cap) were trained at N=10,000 at first, with the three MSE conditions dropped for that size. Once time allowed, all three MSE conditions (mse_unw, mse_wgt, mse_cap) were completed too, so the full 2×3 factorial (both losses × three weighting strategies) is now done at both dataset sizes — §9.2 reports all 6 conditions at N=10,000.

Cost diagnostic. A 100-LC timing probe at mu0=9 and mu0=10 (n_cut=2500, same filters as production) found generation costs ~2.5s per accepted GRB at these values, versus ~0.4-0.9s at the natural mu0=1.16 — and only a ~9% exact-match rate to the target bin (vs. the naive Poisson-mode estimate of ~12.5%), because n_cut=2500 — a shared pulse-count budget across a whole light curve's avalanche — is hit far more often when mu0 itself is 9-10, discarding many otherwise-plausible candidates. This cost is specific to the uni (uniform-by-construction) harvesting method, which sweeps mu0 per target bin (§7.11) — it is why generate_uniform_bins.py gained a --max-bin argument, and why both uniform_3000/uniform_10000 were capped below the originally planned 1-10 range. The same growth curve kept biting at the smaller cap too: uniform_3000 finished bins 1-8 without issue, but uniform_10000 (needing more than 3x as many matches per bin) hit a wall at bin 7 — its harvest rate dropped to roughly a quarter of bins 1-6's pace — so bin 8 was dropped for that dataset specifically, leaving uniform_10000 capped at bins 1-7 rather than 1-8 (§7 overview table, §10).

Why is the mu0=10 distribution so much more symmetric/Gaussian-looking than the natural one, when both are draws from the same kind of process (Poisson(mu0), §2.1)? This is a generic property of the Poisson distribution, not something specific to this pipeline. A Poisson(λ) variable has skewness = 1/√λ and excess kurtosis = 1/λ — both shrink as λ grows, so the distribution becomes progressively more symmetric and bell-shaped as its mean increases, converging toward a Gaussian in the large-λ limit (the discrete analogue of the Central Limit Theorem: a Poisson(λ) can be thought of as a sum of λ independent Poisson(1) contributions, and sums of many i.i.d. variables trend Gaussian). At mu0=1.16 (skewness ≈ 0.93), the distribution is also hard up against its natural lower bound at zero — it cannot go negative, so probability mass piles up at 0-2 with a long thin tail, which reads visually as a sharp spike-and-decay rather than a bell. At mu0=10 (skewness ≈ 0.32), the mode sits far enough from that zero boundary that the distribution has room to spread symmetrically on both sides, which is exactly what the chart shows. This would happen for any mu0 pushed similarly far from zero, regardless of the astrophysics — it's arithmetic, not physics.

The pattern across every regime and size: reweighting existing rare examples (wgt) consistently reaches further into the tail than any resampling of the same underlying data (cap), and capping only ever helps as a side effect of accidentally tying several classes at exact parity — never by rescuing classes that were rare to begin with. The one case where none of this matters is when the data isn't imbalanced in the first place (uni), where the question resolves to loss function alone rather than sampler strategy.

Just creating synthetic LCs — no GA involved anywhere in this pipeline.

simulate_GRBs.py (which is what's generating the 10k/20k datasets) only draws light curves from the SS96 avalanche model using the 7 parameters already sitting in config.ini — the ones from the paper's already-completed GA fit (mu=1.34, mu0=1.16, alpha=2.53, delta1=-0.75, delta2=0.27, tau_min=0.03, tau_max=56.8). It never touches geneticgrbs.py (the actual GA optimizer, which searches for those parameter values by fitting against the real Swift/BAT catalog) — that would additionally need the real catalog data, which we established early on isn't available on this machine and isn't needed for what we're doing.

So the full chain is: GA fit already done by the original authors (real data → 7 numbers, not run by us) → our pipeline draws synthetic LCs from those fixed 7 numbers → CNN trained to predict n_parent_pulses from those synthetic LCs. This is exactly the distinction covered in REPORT.md §7.4 (why real Swift/BAT LCs should statistically resemble ours despite never touching the catalog ourselves).
